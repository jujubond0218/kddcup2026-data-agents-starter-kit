# Phase 1 Python 执行生命周期修复

## 问题与复现

`execute_python` 原先在任务子进程内再次使用系统默认 `fork` 创建执行进程，并通过
`multiprocessing.Queue` 返回结果。Runner 又从 `ThreadPoolExecutor` worker 中创建
任务子进程，因此完整结构是“线程并发 → 任务 fork → Python fork → Queue”。

2026-07-30 在合并 PR #7 后，从最新 `origin/master` 并发重跑 `task_11`、
`task_24`、`task_38`，run ID 为 `20260730T103251Z`。`task_24` 成功且满分；
`task_11` 与 `task_38` 再次触发 120 秒任务硬超时。两题最后活动均为
`execute_python` 的 `tool_started`，分别持续约 108.620 秒和 87.788 秒，没有对应的
`tool_completed` 或 `tool_failed`。

将两题及此前同类 bad case 实际生成的 Python 代码脱离 Runner 原样重放后，执行时间
只有约 0.05 至 0.17 秒。相同代码在接近 Runner 的嵌套并发结构中重放 30 次时，有
3 次外层任务进程无法退出；加入阶段探针改变调度后，100 次没有复现。这些证据说明问题
不是数据规模或 Python 计算性能，而是与调度时序有关的进程生命周期竞争。现有事件粒度
不足以证明具体卡在 stdout/import 锁、进程 join 还是 Queue feeder，但可以确定故障位于
Python 工具内部的启动、结果回传或回收路径。

## 修复

Python 执行进程改为显式使用 `multiprocessing.get_context("spawn")`，从干净解释器
启动，不继承主 Agent、HTTP 客户端或并发线程可能持有的锁。结果通道改为单向 Pipe：
子进程同步发送一个成功或失败字典，父进程使用有界 `poll` 等待，不再调用不可靠的
`Queue.empty()`，也不存在无限期 `Queue.get()`。

超时和退出回收全部改为有界流程：

```text
等待 Pipe 结果
  → 到期后 terminate
  → 最多等待 1 秒
  → 仍存活则 kill
  → 最多等待 1 秒
  → 返回结构化超时结果
```

子进程正常发送结果后，父进程也只做有界 join；子进程异常退出且没有发送结果时，Pipe
关闭会立即使父进程返回“exited without returning a result”，不会等待完整任务预算。
该改造只隔离进程生命周期，不把 `execute_python` 描述为操作系统安全沙箱。

## stdout/stderr 返回边界

进程生命周期有界并不等于返回给模型的 observation 有界。Python 子进程仍可把任意体积的
stdout 或 stderr 写入临时文件；如果父进程把文件完整读回，单次工具结果就可能挤满下一轮
模型请求。因此，运行时现在分别将返回的 stdout 和 stderr 限制为 64 KiB。小于上限的输出
保持原有结构和内容；超过上限时保留开头与结尾，中间插入显式截断标记，并在顶层返回
`truncated: true` 和 `capture.output`、`capture.stderr` 元数据，其中包括原始、返回和省略的
字节数。

上限只作用于父进程返回的 observation，不在子进程写出时提前关闭 stdout/stderr，也不改变
30 秒执行上限、Pipe 结果回传、异常 traceback 或 terminate/kill 回收路径。按字节取首尾时会
避开 UTF-8 字符边界，避免因为截断人为产生替换字符。自动化测试覆盖小输出结构不变、stdout
与 stderr 独立截断、UTF-8 边界、截断后异常回传，以及下一轮模型请求收到有界 observation。

## 300 秒任务上限的 50 题实验

为区分 Python 生命周期修复与原 120 秒任务硬超时的影响，随后保持 Python 工具自身
30 秒上限不变，只把 Runner 单任务硬超时临时提高到 300 秒，以 `max_workers=4`
运行 50 题。run ID 为 `20260730T140345Z`。事件时间戳显示实际墙钟时间为
647.938 秒，任务耗时中位数为 32.486 秒，P95 为 111.831 秒。

Runner 成功 42/50；评分为 **0.6393**，34/50 题取得非零分，其中 30 题满分、
4 题部分匹配、8 题无匹配、8 题缺失。本轮没有任务触发 300 秒硬超时。失败任务中，
`task_173`、`task_199`、`task_344`、`task_396`、`task_418`、`task_420` 耗尽
20 步；`task_38` 的模型请求在两次尝试后超时；`task_250` 因输入超过模型接口允许的
长度而被拒绝。

全轮共有 136 次 `execute_python`，136/136 均形成 `tool_completed`，没有未配对的
`tool_started`。调用耗时中位数为 2.380 秒，最大值为 13.074 秒，没有调用超过
30 秒后失联。两次 Python 代码执行失败也分别在 1.836 秒和 2.160 秒正常返回失败结果，
说明异常路径同样没有卡死。

作为非严格参照，先前 120 秒单轮 `20260730T092318Z` 为 Runner 成功 39/50、评分
0.6047、11 题缺失；本轮成功 42/50、评分提高约 0.0347、缺失降至 8 题。两轮同时
存在 Python 实现差异、任务超时配置差异和真实模型波动，不能据此拆分各因素的因果贡献。
300 秒只用于本次实验，没有修改项目默认的 120 秒任务硬超时。
