# Phase 1 步数预算提醒与停止守卫

## 改造动机

在 Python 生命周期修复后的 300 秒全量实验中，`task_173`、`task_199`、
`task_344`、`task_396`、`task_418` 和 `task_420` 均耗尽 20 个 ReAct 步骤而没有
提交答案。其中部分轨迹已经得到候选结果，却继续重复分析或开始新的探索。增加任务超时
不能解决这种不收敛，也无法保证额外步骤带来新证据。

本改造只让主 Agent 感知剩余步骤，并为最后一步误选分析工具提供一次有界的提交机会。
它不读取 gold、不判断答案语义，不修改 Verifier、Scorer、Explorer、工具 schema 或
`max_steps` 配置。

## 运行时行为

主循环在模型请求前根据已经使用的正常步骤注入两条一次性用户消息：

- 70%：已有证据足够时提交，否则只做最高价值的剩余核验并停止重复工作；
- 90%：优先提交已有证据支持的答案，不再开始宽泛探索。

默认 `max_steps=20` 时，两条消息分别出现在第 15 和第 19 次请求前。它们只进入正常消息
历史，不额外消耗步骤。

若第 20 步返回一个有效的非 `answer` 工具调用，且 Explorer 已完成、当前注册表包含
`answer`，运行时会：

```text
assistant.tool_call(non-terminal)
  → 不执行 handler
  → matching tool_call_id + FINAL_STEP_REQUIRES_ANSWER
  → 第 21 次请求只暴露 answer
  → 成功：复用参数校验和 Verifier 后终止
  → 失败：不再重试，保留既有 max_steps failure
```

被阻断调用仍作为第 20 个失败 Step 写入 Trace，第 21 个收尾调用也使用现有 Step 字段。
被阻断工具不会产生 `tool_started`；新增 `final_step_guard_triggered` 记录 call ID、
工具名和重试步骤。预算消息使用 `step_budget_warning` 记录级别、已用步数和剩余步数。
收尾模型请求的事件带 `finalization_retry=true`。

守卫不会绕过强制 Explorer 首轮；若最后一步仍处于 `exploration_pending`，当前工具集中
没有 `answer`，`explore` 会按原行为执行并最终因步骤耗尽失败。最后一步直接调用
`answer`、协议错误或 Verifier 拒绝也保持原行为，不会获得额外收尾循环。

## 自动化验证

Scripted model 测试固定以下契约：

- 70% 与 90% 提醒在第 15、19 次请求前各出现一次，提前提交不触发守卫；
- 最后一步的非终止 handler 不执行，错误 observation 保留原始 call ID；
- 第 21 次请求只暴露 `answer`，合法答案正常通过 Verifier；
- 收尾请求返回非 `answer`、空调用、非法参数或非法答案时均只执行一次；
- Explorer pending 不被绕过，Runner 能落盘第 21 步、守卫事件和最终预测。

测试同时保持现有原生调用、答案纠错、硬超时、恢复和事件语义兼容。停止守卫目标文件
共 13 项测试通过，全量为 119 passed；Ruff、改动文件格式、lock 和
`git diff --check` 通过。全仓格式检查仍报告 `run/__init__.py` 与
`tools/filesystem.py` 两个 `origin/master` 既有文件需要格式化，本 PR 不修改它们。

## 定向实验与结论边界

固定样本位于 `configs/stop_guard_bad_cases.example.txt`。主样本是上述 6 个步骤耗尽
任务，`task_80` 作为负向观察：它曾大量重复 Python，但在参考运行中已经提交且语义得分
为 0，可用于防止把“更早提交”误报为准确率提升。

真实模型实验统一使用 300 秒任务硬超时、`max_steps=20`、4 workers、20 秒模型请求
超时和一次重试。先运行 7 题定向集；只有至少一个主样本从缺失变为非零得分，且
`task_80` 不从成功提交退化为缺失时，才进行一次 50 题全量复核。

协议测试能够确定守卫是否有界、call ID 是否正确以及 handler 是否未执行；真实实验才能
观察提交率和得分。新增预测、Runner 成功率和语义准确率必须分别报告。若只把缺失预测
变成零分答案，本改造不能宣称提高准确率。

## 300 秒定向实验结果

自动化检查通过后，使用上述 7 题、300 秒任务硬超时、`max_steps=20`、4 workers、
20 秒请求超时和一次重试完成一次定向运行，run ID 为 `20260731T032115Z`。结果为：

| 任务 | Runner | 预算提醒 | 最终守卫 | 定向 score |
| --- | --- | ---: | ---: | ---: |
| `task_173` | 成功 | 2 | 0 | 0 |
| `task_199` | 成功 | 0 | 0 | 0 |
| `task_344` | 成功 | 2 | 1 | 0 |
| `task_396` | 步骤耗尽 | 2 | 1 | 0 |
| `task_418` | 成功 | 2 | 1 | 0 |
| `task_420` | 成功 | 2 | 1 | 0 |
| `task_80` | 300 秒硬超时 | 0 | 0 | 0 |

四个任务触发最终守卫，其中 `task_344`、`task_418`、`task_420` 在第 21 步提交，
但答案均为 no-match；`task_396` 的收尾请求仍未形成有效答案。另有 `task_173` 和
`task_199` 未经最终守卫便提交，同样均为 no-match。因此本轮把部分缺失预测转成了
Runner 成功，却没有产生任何非零语义得分。

`task_80` 在第 4 步 `execute_python` 期间触发任务硬超时，尚未到达 70% 提醒或最终
守卫，所以该超时不能归因于本改造；但预先约定的负向观察门槛仍未满足。按照实验方案，
本轮不继续进行 50 题全量实验，也不增加更强的停止规则。当前证据只支持“守卫协议按设计
有界运行”，不支持“停止守卫提高准确率”。
