# Phase 1 连续相同工具调用守卫

## 问题与范围

上下文输入测量显示，部分任务的主要增长来自多轮工具历史，而不是单条 SQL 或 schema 结果。
`task_396` 的一次真实运行中，14 次 `execute_python` 只有 8 种参数，其中一份参数连续重复
6 次，同一 observation 最多重复 9 次。重复结果不仅占用上下文，也消耗 Python 子进程、模型
请求和有限步骤。

本改造只处理最明确的连续循环：同一已注册非终止工具使用相同校验后参数连续调用。它不比较
自然语言语义、不计算 observation 相似度、不总结历史，也不阻止参数不同的连续 SQL、文件读取
或 Python 调用。

## 运行规则

工具参数先由现有 Pydantic schema 校验并转换为 JSON 形式，再按 key 排序生成仅存在于任务
进程内的调用指纹。因此参数 key 顺序不同、显式填写默认值和省略默认值不会绕过计数。

- 第 1、2 次连续相同调用正常执行；
- 第 3 次及以后不进入 handler，返回 `REPEATED_IDENTICAL_TOOL_CALL`；
- 更换工具或修改校验后参数会清零计数；
- `answer`、`explore` 和 `commit_evidence_plan` 不参与该规则。

拦截 observation 保留当前模型调用生成的原始 `tool_call_id`，标记 `recoverable` 和
`do_not_retry_same_call`，并引导模型复用先前结果、回看已有证据、Explorer 报告或计划，随后
改变参数、来源或方法，或者提交当前证据支持的最佳答案。运行时不把原参数和 observation 写入
专用事件；`repeated_identical_tool_call_blocked` 只记录工具名、step、连续次数和前序 step。

## 边界

该规则是有意保持简单的控制面保护，不声称相同调用必然语义无效。同一段 Python 如果依赖
持久化文件副作用并且确实需要连续执行三次，也会在第三次被拦截；当前只读数据分析任务中，
这种模式预计少于无进展循环。第一版不增加代码语义归一化、相似参数判断、动态阈值或 LLM
summary，后续是否扩大范围必须由真实重复率、Runner 结果和语义评分共同决定。

## 三次真实任务观测

实现后使用同一配置顺序运行 `task_396` 三次，run ID 为 `20260810T145353Z`、
`20260810T145611Z` 和 `20260810T145844Z`。三轮都执行到 21 个记录步骤，重复调用守卫均未
触发：前两轮分别尝试 16、14 次 Python，第三轮 14 次 Python 参数全部不同。前两轮没有
提交答案；第三轮提交了答案但 scorer 状态为 `no_match`。最大请求体分别约 62.9 KB、
134.4 KB 和 71.7 KB，服务端最高 prompt tokens 分别为 14,276、28,021 和 15,214。

因此这三轮不能证明守卫提高了 Runner 成功率、上下文大小或答案质量，只说明它没有误拦参数
持续变化的探索。作为回溯核验，守卫前的 `20260810T141543Z` 轨迹确实存在 6 次连续、工具名
和校验后参数完全相同的 `execute_python`；按当前规则，前两次会执行，后四次会被短 observation
拦截。真实服务路径具有波动性，自动化测试负责固定“第三次不进入 handler”和 call ID 对齐，
历史轨迹只证明该规则覆盖已观察到的精确循环形态，不代表未来任务必然触发。
